# Parametric Mineral Crystal Viewer — Implementation Plan

# 1. Implementation Sequence

Recommended implementation sequence for crystal systems:

```text
1. Cubic
2. Tetragonal
3. Hexagonal
4. Trigonal
5. Orthorhombic
6. Monoclinic
7. Triclinic
```

The order may be changed if required by the selected prototype minerals.

---

# 2. First Complex Prototype

Quartz is the first complex prototype, after the generic engine and a simple cubic mineral validate the architecture.

The quartz implementation should support:

* trigonal crystallography
* hexagonal coordinate setting
* prism forms
* positive and negative rhombohedra
* several named habits
* face identification
* morphology sliders
* left/right handedness where applicable

This establishes whether the architecture can correctly generate recognizable crystal forms for a non-trivial system.

---

# 3. Development Milestone 1 — Geometry Prototype

Deliver:

```text
unit-cell mathematics
reciprocal lattice
Miller planes
symmetry resolution and input validation
validated operation registry sufficient for the cubic prototype
half-space intersection
generic crystal geometry output
explicit invalid-geometry diagnostics
```

No polished UI required.

Implement the symmetry contract in spec §5.2 and §7 during M1. Expand registry coverage with the later crystal-system and CIF milestones; a complete space-group registry is not required for the first prototype.

Required symmetry tests:

* Explicit operations and registry lookup produce equivalent results.
* Conflicting identifiers and operations are rejected before geometry generation.
* Missing symmetry is rejected; explicitly requested identity-only symmetry is accepted.
* Miller indices transform correctly in a non-orthogonal basis.
* Opposite faces and inversion symmetry are not added unless generated by the supplied operations.
* Space-operation translations affect atomic positions but not generated face directions.
* Operation sets satisfy identity, closure, inverses, and unit-cell metric compatibility under documented tolerances.

Success criterion:

> Given a simple set of crystallographic forms, the engine generates the expected convex crystal.

Required acceptance tests (spec §9, §10, and §39):

| Input | Expected result |
|---|---|
| Six enclosing cube planes | Valid closed polyhedron |
| All forms disabled or zero development | `no-active-forms` |
| Prism planes without end caps | `unbounded` |
| Prism planes with enclosing end caps | Valid closed polyhedron |
| Redundant plane outside an enclosed crystal | Valid; no face generated for the redundant plane |
| Invalid settings followed by valid settings | Diagnostic, then successful generation |
| Same shape at different supported morphology scales | Same validity classification |

Define scale-relative tolerances and test degenerate-result and numerical-failure diagnostics. At viewer integration, also verify that an invalid edit retains the last valid mesh with an exposed stale status, an initially invalid request displays no mesh, and a subsequent valid edit clears the diagnostic and replaces the mesh (spec §17).

# 4. Development Milestone 2 — Simple Cubic Mineral

Implement a mineral such as fluorite or pyrite.

Support combinations of:

```text
cube
octahedron
other common forms
```

Success criterion:

> Relative form-distance changes produce correct transitions between common cubic morphologies.

# 5. Development Milestone 3 — Quartz

Implement:

```text
trigonal symmetry
Miller-Bravais notation
quartz forms
basic habit presets
morphology sliders
face picking
face labels
```

Success criterion:

> Multiple recognizable quartz habits are produced by the same procedural engine.

---

# 6. Development Milestone 4 — Generic Mineral Definitions

Move all mineral-specific information out of generator code.

Bad:

```ts
function generateQuartz() {}
```

Correct:

```ts
generateCrystal(mineral, morphology);
```

The engine must work from generic data.

# 8. Development Milestone 6 — CIF / Structural Data

Implement:

```text
CIF import
unit-cell display
atomic coordinates
symmetry expansion and periodic bond resolution
atomic structure rendering
```

Success criterion:

> The viewer can load structural data independently of morphology data.

Required acceptance tests (spec §5.4 and §22):

* Symmetry-independent sites expand into the expected complete reference cell.
* Multiple operations producing the same image of a source site do not duplicate atoms.
* Complete-cell data is not expanded a second time.
* Distinct partially occupied source sites are preserved, including coincident alternatives.
* Periodic bonds connect the correct images across cell boundaries.
* Incompatible cell/basis combinations are rejected; explicit basis transformations preserve the structure.
* Atomic structure, unit-cell overlay, and morphology have consistent orientation.
* Missing bonds permit an atoms-only view, and inferred bonds are identified as derived.
* Ambiguous site representation produces an import diagnostic.

# 13. Recommended First Implementation Target

Build one minimal vertical slice through the full stack (see spec §8 for the generation pipeline):

```text
Cubic mineral data (fluorite or pyrite)
    ↓
CrystalGeometry
    ↓
Three.js BufferGeometry
    ↓
plain HTML canvas viewer
    ↓
morphology sliders
```

This validates the entire architecture end-to-end with the simplest crystal system before expanding to trigonal (quartz) and the remaining systems.

---

# 14. Definition of Successful V1

Version 1 succeeds when the goals in spec §1 are met within the scope defined by the milestones (§3–12): framework-independent core, procedural generation from crystallographic data, several crystal systems, at least 5 minerals with multiple documented habits each, morphology sliders, face inspection, axes and unit-cell display, structural/morphology separation, serializable state, citable sources, Three.js as rendering only, and no manually modeled meshes.

---

# 15. Priority Order

The development milestones define the implementation order; see the milestone sections above.

Do not implement advanced visual features before the generic crystallographic generator is validated.

This version deliberately excludes the separate AI/data-extraction roadmap.
